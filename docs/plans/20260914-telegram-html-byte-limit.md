# Исправление обрезания Telegram-дайджеста по байтовому лимиту HTML

## Overview

Добавить независимый предел размера исходного HTML: не более 34996 байт UTF-8 на сообщение.
Сохранить message_limit для отображаемых символов и ограничение 500 блоков. Разбивать
дайджест только между книгами; у отдельной слишком большой книги сокращать только
Content.

## Context

- internal/digest/render.go проверяет отображаемые руны и блоки. Размер HTML с тегами,
экранированным текстом и URL сейчас не ограничен.
- Telegram документирует 32768 отображаемых символов и 500 блоков: [Rich Message
Limits](https://core.telegram.org/bots/api#rich-message-limits).
- В TDLib исходный HTML проходит через clean_input_string:
[RichMessage.cpp](https://github.com/tdlib/td/blob/master/td/telegram/RichMessage.cpp#L109).
- clean_input_string молча обрезает строку около 35000 байт и возвращает успех. Проверка new_size >=
LENGTH_LIMIT - 3 может обрезать ASCII уже при 34997 байтах; 34996 — безопасный предел исходной
строки: [misc.cpp](https://github.com/tdlib/td/blob/master/td/telegram/misc.cpp#L69).
- Это объясняет обрыв внутри продавца без ошибки API. Точное место обрезания
сегодняшнего дайджеста нельзя воспроизвести по предоставленным логам: исходного
отправленного HTML в них нет.
- internal/app/service.go подтверждает книги после успешной отправки каждого Chunk. Поэтому sent:30
отражает подтверждение API, а не проверенную полноту текста.
- Зависимости и новые настройки не нужны. SDK и схему bbolt менять не требуется.

## Development Approach

- Testing approach: Regular — реализация, затем регрессионные тесты в каждой задаче.
- Выполнять задачи последовательно; перед следующей задачей должен проходить make
test.
- Сохранить единый контракт RenderBook для предварительной проверки новых книг и
формирования pending.
- Использовать существующие testify, httptest и временные базы. Проверки не обращаются к
рабочим Alib и Telegram.
- Коммитить завершённые изменения только после успешного make verify.

## Post-Completion

Рабочую базу автоматически не изменять. Повторная отправка сегодняшних книг
требует отдельного выбора записей: число sent:30 не определяет число потерянных книг.

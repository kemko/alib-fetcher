# Точечное упрощение обработки объявлений и Telegram-адаптера

## Overview

Архитектура проекта соразмерна задаче: бизнес-логика, хранение, транспорт и
жизненный цикл разделены; критические сценарии покрыты тестами. Нашлись три
обоснованных упрощения: общая дедупликация, единый путь рендеринга книги и один
HTTP-клиент Telegram.

Цель — сократить дублирование и лишние ветвления, сохранив поведение сервиса.

## Context

- `internal/alib/parser.go` и `internal/alib/client.go` повторяют правила учёта
  успешных и неудачных объявлений. `parsePages` передаёт вызывающему коду шесть
  результатов.
- `internal/digest/render.go` содержит строгий `Render`, используемый только
  тестами, и рабочий `RenderSendable`. Проверка одной новой книги в
  `internal/app/service.go` запускает формирование целого дайджеста.
- `internal/telegram/sender.go` создаёт два HTTP-клиента с одинаковыми настройками;
  `internal/telegram/updates.go` добавляет context-маркер для выбора между ними.
  Исходники установленного SDK подтверждают, что `WithHTTPClient` просто сохраняет
  переданный клиент.
- `make verify` прошёл: форматирование, lint без замечаний, тесты с race detector
  и сборка. `make coverage`: 92,1%. Проверено на установленном Go 1.27.1;
  заявленный Go 1.26.5 отдельно не проверялся.
- Дополнительные зависимости и новые пакеты не нужны.

## Development Approach

- **Testing approach**: Regular; дополнять существующие регрессии в рамках каждого
  изменения.
- Выполнять задачи последовательно. Перед переходом дальше весь набор тестов
  должен проходить.
- Сохранять порядок источников, идентичность `BuyURL`, учёт ошибок, семантику
  pending, подтверждение доставки, формат сообщений и лимиты.
- Использовать существующие httptest-серверы, временные базы и тестовые адаптеры.
- Каждый завершённый рефакторинг коммитить отдельно после успешного `make verify`.
